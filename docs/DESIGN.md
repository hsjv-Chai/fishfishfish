# 策略与接口约定

## 策略

全部时间戳以 UTC 毫秒保存；日亏损按 Asia/Shanghai 分日。K 线必须连续、严格递增、OHLC 合法，末根必须恰好是最近已收盘桶。每个周期使用 1000 根已收盘 K 线。

EMA 用前 N 项算术平均初始化，然后递推 `EMA += 2/(N+1) × (close-EMA)`。ATR14 用前 14 个 TR 均值初始化，再按 Wilder 递推。首次入场信号使用当前已收盘小时 K 线，突破窗口是其前 20 根，不含本根；下跌离场窗口是前 10 根。

每小时 :00:10 之后首次循环处理信号，超过收盘 60 秒不补开仓。执行延迟、网络阻塞会推迟检查；系统不声称精确在 10 秒时成交。现价相对信号收盘价偏离 0.3% 以上则取消该根信号。站点与上游超过 0.3% 的偏差立即阻止开仓，比等待“持续偏差”更保守。

初始止损距离 `max(2×ATR/close, 1%)`，超过 4% 不入场。风险预算 `E×0.0025`，计算投入时除以 `距离 + 0.0002 + 0.001`，再限制在净值 20% 和策略现金内，向下取整四位小数，最低 1 条。

入场后使用真实成交价建止损。跟踪峰值仅使用入场后的已收盘小时收盘价；止损只上移。离场后第一个不完整小时不计入 6 小时冷却。日切以北京时间新一天第一笔可用估值作为日基准（正常误差约 5 秒）；掉线跨日存在额外误差，日志记录中断，不作精确午夜成交假设。

单笔归零前本站采用 `max(0,floor(stakeUnits + stakeUnits×L×(exit/entry−1) − stakeUnits×L×exit/entry×fee))`。本项目按站点数值运算顺序计算，不额外四舍五入，订单回执到手金额与公式必须一致。

## 订单状态与账目

1. SQLite 同步提交 `pending` 和意图审计记录，再发网络请求。
2. 买入唯一键为 `f-` 加 UUID 十六进制，长度 34，满足站点最大 48 字符限制。网络重试复用同一键。
3. 请求返回后原子更新现金、持仓、订单和审计记录。崩溃发生在请求发出之后、回执入库之前时，恢复后先查仓位与流水。
4. 若唯一的新买入流水与唯一匹配的 BTC/1×/金额仓位对应，恢复该持仓；出现多条未知买入、未知仓位或无法确定状态时暂停。这个恢复依赖“账户不由其他交易者同时操作”的运行约束。
5. 平仓使用已知仓位 ID。网络不确定时可重放获取相同回执；不将超时视为成功，不提前释放策略现金。
6. HTTP 400/401/403/429/503 在核对的站点实现中代表未开仓；无先前不确定请求时，过期信号可以清除。网络丢失、500、结构异常保持不确定状态。
7. 对账核对账户余额变动与新流水总和；交易流水必须属于已知仓位。非交易流水只更新账户对账基线，不更新策略现金。
8. 余额不足以覆盖策略现金时停止。外部存款不会自动扩充 50 条策略预算，策略交易盈利会自然增加后续风险计算基数。

接口响应需 `code:200`；HTTP 错误不降级为成功。交易 API 不接受客户端指定成交价格。站点自 2026-10 起支持 `direction=long|short` 与 1–100 的整数杠杆；本实现的接口层会校验方向、倍数和爆仓价，并按方向结算。**V1 策略仍只使用 BTCUSDT / 1 倍多头**，不会主动开空；无部分平仓或挂单。

方向与杠杆的协议细节：

- 开仓 `POST /api/fish/trade/buy` 接受 `{symbol, amount, leverage?, direction?, idempotency_key?}`；`direction` 缺省为 `long`，`leverage` 缺省为 1。幂等键不含方向和倍数，同一键重试回报的是首次成交的真实形状。
- 平仓 `POST /api/fish/trade/sell` 只接受 `{position_id}`，方向从仓位行读取。响应含 `direction` 与 `liquidated`。
- 结算：`notional = stake × leverage`；多头 `move = exit/entry − 1`，空头 `move = 1 − exit/entry`；`payout = max(0, floor(stake + notional × move − notional × (exit/entry) × 0.0002))`。
- 爆仓价：多头 `entry × (1 − 1/L)`；空头 `entry × (1 + 1/L)`。1× 多头没有可达爆仓价（0），**1× 空头有**（2× entry）。
- 爆仓按固定爆仓价结算为 0，不产生 `market_sell` 流水；只有存在持久化卖出意图时，重放 sell 取得权威的 `liquidated` 结果。没有卖出意图的持仓消失仍按未知外部平仓停机复核。
- 开仓杠杆与方向是仓位的固定属性；V1 只读/对账路径不能把它们当成可变参数。后续 v3 策略若启用做空或杠杆，必须重新回测、重新累计影子并重新通过门槛。

## 故障与恢复

所有已知退出意图优先于新信号。新开仓需要本站、上游、会话、K 线同时健康。本站报价不可用但上游新鲜时，仍可触发向站点发出平仓；两边都没有可信价格时，为保护持仓直接请求退出，平台仍负责取成交价。

429 使用 Retry-After；其他可重试故障按 5/10/20/40/80/160/300 秒退避。拒单或结构不匹配触发暂停。故障邮件按故障键合并，同一持续故障最多每小时重复；发送失败至少间隔 60 秒重试，并在恢复时发一封恢复通知。

最大回撤停机不自动解除。平仓后操作员检查交易流水、告警、数据源，使用：

```sh
python3 -m fishbot --config live.toml resume --reason '已核对故障原因并完成复核' --reset-high-water
```

此命令需要交易进程停止且无持仓、无待确认订单。重置后的高点为当前策略现金；保留审计记录和当天亏损暂停。不要通过编辑 SQLite 清空不确定订单；先在网站核对交易回执并修复对账数据来源。数据库缺失时禁止接管现有真实仓位。

## 回测精度

回测的信号、仓位、风控和订单状态机与运行策略共用。小时信号在下一分钟开盘执行，作为 +10 秒执行的较迟近似；不在产生信号的 K 线上成交。分钟内部止损按 `min(分钟开盘价, 止损线)` 再扣不利成交偏差，跳空不能按旧止损价成交。

分钟 OHLC 无法重建 5 秒路径。回测不使用分钟内高价提前抬升账户净值高点；因此极端走势中实盘风控触发可能不同。压力测试是对执行偏差的敏感性分析，不是现场测得的滑点分布。日收益 Sharpe 按 UTC 日收盘、365 日年化、无风险利率为 0；日亏损规则仍按北京时间。

每段独立从 50 条开始。三种基准是现金、100% BTC 持有、初始 20% BTC 加 80% 现金（不再平衡）。暴露比例表示有风险仓位的时间占比，而非资金比例。最终测试段至少 30 笔自然完整交易；段末强制清仓单独列示。

代码哈希、数据哈希和检查结果是本机可审计证据，不是抗管理员篡改的安全边界。任何参数研究都必须保留旧报告并选择新的真正未见数据评估，不能反复调参迎合已查看的测试段。
